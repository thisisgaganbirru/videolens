# Media validation & source acquisition

Everything about getting a valid media file onto local disk: upload handling, URL download (with SSRF protection), FFmpeg-based duration checks and normalization.

**Files** (all under `backend/app/infrastructure/media/`)
- `uploads.py` — `save_upload` (streams an uploaded file to disk in 1MB chunks, extension allowlist, size cap), `create_run_dir`/`cleanup_run_dir`, `validate_temp_dir` (startup guard, below).
- `ffmpeg.py` — `_media_binary` (resolves the ffmpeg/ffprobe path, either from `FFMPEG_LOCATION` or `PATH`), `probe_duration_seconds`, `enforce_duration_cap`, `normalize_media` (re-encodes to H.264/AAC mp4 if a video stream is present, else mp3), `_has_video_stream`. `_has_video_stream` reads only the first CSV field of ffprobe's output: a stream with side data (phone rotation matrix, the ambient-viewing block on Instagram VP9 reels) prints `video,` not `video`, and the old exact match sent those files down the `-vn` mp3 path, losing the picture, or failing with "Output file does not contain any stream" when there was no audio either. Fixed 2026-10-28; `tests/infrastructure/media/test_ffmpeg.py`.
- `net.py` — `validate_public_url` (**SSRF guard**), shared by every resolver.
- `deadline.py` — `DownloadDeadline`, `run_download` and `DOWNLOAD_EXECUTOR`: the wall-clock bound on every link download and the bounded thread pool they run on (below).
- `process.py` — `run_process`: the one way ffmpeg/ffprobe are started, with a timeout, killed on timeout and on cancellation.
- `ytdlp_net.py` — `GuardedYoutubeDL`, the only `YoutubeDL` the app builds: every yt-dlp request goes through `net.py`'s pinned connections, and only native downloaders run (below).
- `ytdlp_downloader.py` — `_cookie_options`, `download_url` (the yt-dlp fetch itself), and the multi-slide helpers (`_collect_slides`, `_fetch_image`, `_skip_entries_without_media`; see "Multi-slide posts" below).
- `captions.py` — `fetch_captions`, the subtitle salvage path used when every resolver has failed.
- `resolvers/` — one route per file plus the chain that orders them: `ytdlp.py` (`YtDlpResolver`), `direct_http.py` (`DirectHttpResolver`), `chain.py` (`ResolverChain`).
- `thumbnails.py` — history poster + display size (Phase 5a): `thumbnail_urls_from_info`, `dimensions_from_info`, `parse_video_dimensions`/`probe_dimensions` (ffprobe, rotation-aware), `fetch_image` (SSRF-guarded), `extract_frame`, `encode_thumbnail`, `build_thumbnail`. See the section below.
- `service.py` — `MediaService`, the single adapter that composes all of the above into the `MediaProcessor` port the use cases depend on.

**Resolver chain**: `MediaService.download_url` no longer calls yt-dlp directly — it delegates to a `ResolverChain` of `domain.ports.SourceResolver` implementations, tried in order. Each resolver declares `can_handle(url)` and is skipped when it says no; a resolver that raises `MediaValidationError` is treated as "this route did not work" and the chain moves on, while any other exception propagates immediately (a bug must not be silently retried away). Current order:

| # | Resolver | Claims | Notes |
|---|---|---|---|
| 1 | `YtDlpResolver` | every URL | Primary path; yt-dlp's generic extractor is itself a fallback for plain links. The only resolver that returns `SourceMetadata`. |
| 2 | `DirectHttpResolver` | URLs whose path ends in an allowed extension | Plain stdlib HTTP GET. Recovers links yt-dlp declines (unknown host, odd content type, stale extractor). No metadata. |

Ordering yt-dlp first is deliberate: nothing that works today changes behaviour, and the fallback only ever runs after the primary has already failed. When every route fails, the **first** resolver's error is the one raised — it is the primary path and carries the curated guidance (the Instagram cookie message), whereas a fallback's failure is usually a bare 404. Adding a source is a new resolver plus one line in `MediaService`; `MediaProcessor` and `ProcessRunUseCase` are untouched.

`DirectHttpResolver` builds its opener with `_ValidatingRedirectHandler` (since Phase 5a this lives in `net.py` as `ValidatingRedirectHandler`, re-exported under the old name, so the thumbnail fetch shares the one copy), which re-runs `validate_public_url` on **every redirect hop** — validating only the submitted URL would let a public host bounce the fetch to `169.254.169.254`. It enforces `MAX_FILE_SIZE_MB` twice: against `Content-Length` before reading a byte, and again while streaming (a server can lie or omit the header). It uses `urllib.request` rather than `httpx` because httpx is only present transitively via `google-genai`; taking a direct dependency would mean re-pinning the hash-locked `requirements.txt` for a fallback path.

**Caption recovery** (`captions.py`): `fetch_captions` is not a resolver — it returns a transcript, not media, so it cannot satisfy `SourceResolver`. It is reached from `ProcessRunUseCase` only after the whole chain has failed. It prefers publisher-written subtitles over auto-captions, prefers `json3`/`vtt`/`srt` in that order (least parsing first), falls back to any available language rather than giving up, and strips cue scaffolding down to plain text — collapsing the duplicated rolling-window lines auto-captions emit, which would otherwise triple the token cost and read as a stutter. It **re-applies the run's duration limit** (`MAX_DURATION_SECONDS`, or the signed-in BYOK value for that run) from the info dict: the duration cap is a product policy about how much media gets analyzed, and a caption track must not become a way around it. Every expected miss returns `None` rather than raising, because the caller is already handling a failed download and needs a yes/no, not a second error to reconcile. The track itself is fetched by `_fetch_track` through `build_public_opener()` (checked and pinned per request, every redirect re-checked, `http`/`https` only), 30 s timeout, read in 64 KB chunks under `MAX_CAPTION_BYTES` (**5 MB**; declared `Content-Length` and the actual body both checked). Its URL comes from the fetched page — a `<track src>` on a generic page becomes a subtitle URL — so before 2026-11-20 a page could point it at `169.254.169.254` and get the response back as the transcript (review finding H1).

`_source_metadata_from_info` was extracted out of `ytdlp_downloader.download_url` so both paths build `SourceMetadata` identically — the publisher's post metadata is available from `extract_info` whether or not the media bytes are.

**SSRF protection**: `validate_public_url` in `net.py` parses the URL, requires `http`/`https` with no embedded credentials, then does a real DNS resolution (`socket.getaddrinfo`) and checks **every** resolved address with `is_public_address` — `is_global`, not multicast, and for IPv6 not a translation form (IPv4-mapped, 6to4, Teredo, NAT64 `64:ff9b::/96` and `64:ff9b:1::/48`) wrapping a non-public IPv4 address; `ipaddress` alone calls `64:ff9b::7f00:1` global — rejecting private/local/link-local targets *before* any resolver touches the URL. It returns the approved address.

**Pinned connections (2026-11-07)**: checking a name and then letting urllib resolve it again is the DNS-rebinding hole (the name answers a public address to the check and a private one to the fetch). `build_public_opener()` is the one urllib opener for outbound fetches (`DirectHttpResolver`, the thumbnail fetch): its `PublicHTTPHandler`/`PublicHTTPSHandler` run the check for every request they open — the first one and every redirect hop — and then connect `PinnedHTTPConnection`/`PinnedHTTPSConnection` to the *approved address*, with the URL's hostname kept for the Host header and the TLS server name, so certificate verification is unchanged. Through an explicit proxy (`HTTP(S)_PROXY`) the URL is still checked but the connection is not pinned, because the proxy does the resolving.

**yt-dlp inside the guard (2026-11-20)**: yt-dlp does its own resolution, redirects and sub-requests (pages, manifests, segments, embedded media, subtitles), so checking only the submitted URL left all of those unguarded. `ytdlp_net.GuardedYoutubeDL` (used by `download_url` and `fetch_captions`) closes it:
- **Requests**: its request director holds one handler, `PublicUrllibRH` (yt-dlp's urllib handler with `net.py`'s `PinnedHTTPConnection`/`PinnedHTTPSConnection`). Every connection — first request, each redirect hop, each fragment — runs `validate_public_url` at connect time and dials the approved address, so redirects and DNS rebinding are covered. `_PublicRedirectHandler` also refuses a non-public or non-HTTP(S) redirect before the hop. Only `http`, `https` and `data:` URLs are supported (no `ftp`, no `file`). A refusal reaches yt-dlp as a `RequestError` ("Refused by the SSRF guard: ...").
- **Restricted, and what it costs**: yt-dlp's `requests`, `websockets` and `curl_cffi` handlers are not used, because they connect inside third-party code this module cannot pin. Cost: no connection pooling (fragmented HLS/DASH downloads open a connection per fragment, somewhat slower), no HTTPS-scheme proxies, no websocket-based extractors, no browser impersonation (`curl_cffi` was not installed anyway).
- **Downloaders**: only `HttpFD`, `HlsFD`, `DashSegmentsFD`, `F4mFD` and `IsmFD` run; each fetches through `ydl.urlopen`, i.e. the guarded handler. `GuardedYoutubeDL.dl` refuses anything else (`FFmpegFD`, `RtmpFD`, websocket/live downloaders, external tools), `hls_prefer_native` is forced on and `external_downloader` is dropped. HlsFD's own fallback to ffmpeg (for a manifest it cannot play natively) is replaced by `_RefusedFFmpegFD`, which fails the download; the module refuses to import if a yt-dlp release moves `yt_dlp.downloader.hls.FFmpegFD`, so a bump cannot silently re-open it. Cost: live streams, HLS with features the native downloader lacks (SAMPLE-AES and similar), `section_start`/`section_end` cuts and RTMP sources cannot be downloaded. ffmpeg still merges and normalises **local** files; nothing in this flow hands it a remote URL (`ffmpeg.py` and the thumbnail encoder take server-chosen paths or stdin).
- **Proxies**: through yt-dlp's `proxy` option or `HTTP(S)_PROXY`/`ALL_PROXY` (socks included), every request URL and redirect hop is still checked, but the connection goes to the proxy unpinned — the same policy as `net.py`.

This is the load-bearing check that stops someone submitting `http://169.254.169.254/...` or a `localhost` URL to reach internal infra. It lives in its own module precisely so there is one copy: a second implementation that drifts is how a fallback route ends up reaching an address the primary route refuses.

**Limits per caller (2026-11-13)**: the size and duration limits are no longer read from `Settings` at each check. `EntitlementResolver.media_limits(principal, byok=...)` (`application/entitlements.py`) returns a `domain.entitlements.MediaLimits` for the caller: signed in (JWT or account API key) **and** sending `X-Gemini-Api-Key` gets `SIGNED_IN_BYOK_MAX_DURATION_SECONDS` / `SIGNED_IN_BYOK_MAX_FILE_SIZE_MB` (600 s / 500 MB); everyone else, anonymous BYOK included, gets `MAX_DURATION_SECONDS` / `MAX_FILE_SIZE_MB` (180 s / 200 MB). A bigger value at or below the standard one is floored to the standard one. Every enforcement point takes that object as `limits=`: `save_upload` (streamed size), `enforce_duration_cap`, `download_url` (yt-dlp `max_filesize`, the progress hook and the post-download check), `DirectHttpResolver` (Content-Length and streamed size), and `fetch_captions` (the caption track's duration, formerly a direct `settings.max_duration_seconds` read). `infrastructure/media/limits.py`'s `effective_limits` falls back to the standard set when a caller passes `None`, so older call sites and tests keep today's behaviour. The run carries its limits to the worker (`job-queue.md`), so the worker checks the same numbers the API admitted. Messages come from `duration_over_limit_message` / `size_over_limit_message` in `domain/entitlements.py`: same status and `{detail}` shape, plus a hint when a bigger tier would have fit ("Sign in and add your own Gemini key for videos up to 10:00."; "Sign in" for anonymous BYOK, "Add your own Gemini key" for signed in without one). The yt-dlp post-download sentence is now "That video is over the 200MB limit." instead of "Download exceeds the 200 MB size limit.". `GET /api/limits` reports both sets. Since the paid plan (`docs/backend/billing.md`), a third set: `media_limits(principal, byok=, paid=)` gives a paid account `MediaTier.PAID` (`PAID_MAX_DURATION_SECONDS` / `PAID_MAX_FILE_SIZE_MB`, defaulting to the signed-in BYOK numbers) with or without a key, the larger of paid and BYOK when it sends one; `GET /api/limits` gains `paid`. Paid runs take the long job and the per-account long-run slot like signed-in BYOK runs (`MediaTier.long_job`).

**Limits enforced**: file extension (`.mp3`/`.mp4`/`.mov` only), `MAX_FILE_SIZE_MB` (both during streamed upload and post-download for URL sources), `MAX_DURATION_SECONDS` via `enforce_duration_cap` (checked once for uploads, checked again after download for URL/S3 sources since those weren't probed synchronously by the request handler). `enforce_duration_cap` **returns the probed duration** (seconds, float) so callers can record it on the run (`Run.duration_seconds`); `captions.py` likewise carries yt-dlp's reported `duration` on `CaptionTrack.duration_seconds`.

**yt-dlp cookies**: exactly one of `YTDLP_COOKIES_FILE` or `YTDLP_COOKIES_FROM_BROWSER` may be configured — both set raises `MediaValidationError`. Needed for login-gated sources (Instagram in particular); the download-error message is rewritten with cookie-setup guidance when yt-dlp reports Instagram returned an empty response.

**Download size (720p soft cap)**: `_format_options` gives yt-dlp `format: "bestvideo*+bestaudio/best/bestaudio"` plus `format_sort: ["res:<YTDLP_MAX_HEIGHT>"]` (default **720**; `<= 0` drops `format_sort` and restores yt-dlp's plain "best"). The sort prefers the largest variant at or under the cap; a source with nothing that small gets its **smallest** variant above it rather than failing, and formats of unknown height (progressive social-media mp4s) stay eligible. A `[height<=720]` filter in the selector was rejected because its fallback (`/bv*+ba/b`) jumps to the source's best (4K) exactly when no small variant exists, and the filter drops unknown-height formats. Audio-only sources and the caption fallback (`captions.py`, its own options, `download=False`) are unaffected; split streams still merge through the directory of the resolved `ffmpeg` (`FFMPEG_LOCATION`). Why: a 3:33 YouTube link fetched a 229 MiB best format and hit a mid-download 403; FFmpeg re-encodes everything anyway and Gemini doesn't need more than 720p. The probe still wins for `width`/`height`, so the poster/dims path doesn't care.

**Blocked downloads (403/429)**: `_download_failure` maps `HTTP Error 403`, `HTTP Error 429` and `Too Many Requests` to "The site blocked this download for now - the video itself is fine. Try again in a few minutes." These entries sit **after** the private/unavailable/region markers in `_KNOWN_DOWNLOAD_FAILURES`, so a genuine one of those keeps its own sentence. Before this, a mid-download 403 on a public YouTube video fell through to the generic "may be private, deleted, or region-locked", which was untrue. The sentence names only the cause and timing because the frontend's `downloading`-stage `recoveryAdvice` already adds "download the video and upload the file instead". YouTube's "Sign in to confirm you're not a bot" keeps its existing sentence ("YouTube is blocking automated downloads from this server.").

**Geo-blocks**: "This video isn't available in this server's region." is returned when the `DownloadError`'s `exc_info` holds a `GeoRestrictedError` (any extractor, any wording), or when the text carries one of yt-dlp's real geo markers: `available in your country` (YouTube's subreason "The uploader has not made this video available in your country", `extractor/youtube/_video.py`), `not available from your location` / `due to geo restriction` (`raise_geo_restricted`'s default, `extractor/common.py`), or `You might want to use a VPN or a proxy server` (the hint `YoutubeDL.py` appends to every `GeoRestrictedError` it reports). These sit ahead of "Video unavailable" and the 403/429 entries, because a geo-blocked video can also surface an HTTP 403 and the region is the true cause. Strings checked against yt-dlp 2026.07.04; the old marker `not available in your country` never matched YouTube's wording.

**Source metadata**: `download_url` also builds a `domain.entities.SourceMetadata` from the same `extract_info()` call already needed for the download itself (`platform` from `extractor_key`, plus `title`/`uploader`/`uploader_url`/`description`/`upload_date`/`like_count`/`view_count`/`comment_count`, all `dict.get()`-based so missing fields are just `None`) and attaches it to the returned `SavedUpload`. This is platform post metadata, distinct from the Gemini-generated `VideoAnalysis` — see `docs/backend/run-processing.md` for how it's persisted onto the `Run`. File uploads (`uploads.save_upload`) never set this field.

## Multi-slide posts: Instagram carousels (2026-11-26)

An Instagram carousel is one post of up to 20 slides, each a video or a still image; a post that is one photo is the same thing with one slide. Before this, `noplaylist` did nothing for it (Instagram's extractor ignores it), every video slide was written to the same `download.<ext>`, and the first image slide raised "No video formats found" and failed the run. Now a post is downloaded, checked and analyzed as one unit:

- **Download** (`ytdlp_downloader.py`). Still the one `extract_info(url, download=True)` call. Only Instagram links take the slide path: any other site's playlist, set or multi-part link stops after its first entry (`playlistend` 1) and is refused with "This link is a playlist or set. Paste a link to one video or track instead." (`_PLAYLIST_LINK`, `_single_entry_of`), unless it holds exactly one entry, which is then the ordinary single file. Before this a SoundCloud set or a YouTube playlist went down the slide path, downloading up to 20 files and labelling audio as video. The output template is `%(playlist_index&slide-{:02d}|download)s.%(ext)s`: a playlist entry becomes `slide-01.mp4`, `slide-02.jpg`..., a single file keeps `download.<ext>`. `playlistend` is `MAX_SLIDES` (20, Instagram's own limit) for Instagram. For Instagram links only, `ignore_no_formats_error` lets an image entry through extraction and the `match_filter` `_skip_entries_without_media` skips it at download time (an entry with no media URL would otherwise make `YoutubeDL.dl` raise); its info, whose `thumbnails` are every rendition of the photo, stays in the result. `_collect_slides` then walks the entries in order: a downloaded file is a `VIDEO` slide, an Instagram image entry gets its largest rendition fetched by `_fetch_image` through the downloader's own `urlopen` (so on `net.py`'s pinned connections, with the entry's `http_headers`, under the run's deadline), sniffed as JPEG, PNG or WebP and saved under its real extension. An entry with neither is skipped and logged; a post with no slide left fails with "This post has no video or image we could download.". A one-video "post" goes back to the single-file path unchanged.
- **Size**: the progress hook sums bytes across every file being written, so a post's slides (and a video's split streams) share one `MAX_FILE_SIZE_MB` budget; images count against what is left, and one image is capped at 15 MB. The post-download check uses the total ("That post is over the 200MB limit.").
- **Probe and cap** (`ffmpeg.enforce_slides_cap`, `MediaProcessor.enforce_slides_cap`): every image slide must decode as `mjpeg`/`png`/`webp` (`probe_image`, which runs the same playlist sniff and demuxer refusal as every probe), and the video slides' lengths are summed against the run's duration limit ("The videos in this post are 4:10 long. The limit is 3:00."). Images take no time. The total is what the long-run slot counts.
- **Normalize** (`ffmpeg.normalize_slides`): videos through `normalize_media` (now with a `name=` stem, so outputs are `normalized-01.mp4`...), images re-encoded by `normalize_image` to a JPEG no larger than `MAX_SLIDE_IMAGE_SIDE` (2048 px) on the longest side, never enlarged, metadata dropped.
- **Result**: `SavedUpload.slides` carries `MediaSlide(path, kind)` in order, with `path` the first slide and `thumbnail_urls`/`width`/`height` from the first slide's entry, so the poster is the post's cover.

Not covered: TikTok photo posts and other sites' multi-item posts; they are refused as playlists (or analyzed as their single entry), and image entries are fetched for Instagram links only. Instagram serves carousels only through its API and GraphQL paths, both of which want a logged-in `YTDLP_COOKIES_FILE` in practice. Tests: `tests/infrastructure/media/test_ytdlp_carousel.py` (real yt-dlp processing against a local server), `test_ffmpeg_slides.py` (real binaries).

## History poster: thumbnail and display size (Phase 5a)

`MediaService.describe_visuals(media_path=, thumbnail_urls=, width=, height=, duration_seconds=) -> MediaVisuals` (the `MediaProcessor` port method) produces what the browser stores in its IndexedDB History. It **never raises**: the whole step is wrapped in a 45 s `wait_for` and any error returns empty `MediaVisuals`.

**Dimensions**: `ffprobe -select_streams v:0 -show_entries stream=width,height:stream_disposition=attached_pic:stream_tags=rotate:stream_side_data=rotation -of json`. A ±90/270° rotation (display-matrix side data on new files, `rotate` tag on old ones) swaps width/height so phone portrait video reports portrait. An `attached_pic` stream (MP3 cover art) counts as no video. The probe wins; yt-dlp's `width`/`height` are the fallback (and the only source on the captions path). Audio → `None`.

**Thumbnail, in order**:
1. yt-dlp's `info["thumbnail"]`, then the best `info["thumbnails"]` entry (by `preference`, then area) — at most two URLs, http(s) only. Fetched with `urllib` through `validate_public_url` **and** `ValidatingRedirectHandler` (every redirect hop re-checked), 8 s timeout per socket read, **3 MB cap** (declared `Content-Length` and the body both checked). Since 2026-11-20 the fetch runs through `run_download` on `DOWNLOAD_EXECUTOR` with its own 10 s `DownloadDeadline` (`FETCH_DEADLINE_SECONDS`; not the run's download budget) and reads in 64 KB `read1` chunks, checking the deadline and the cap per chunk, so a server trickling a byte every few seconds no longer holds a thread past 10 s.
2. Otherwise (no URL, fetch failed, or ffmpeg couldn't decode it): one frame from the local media at `min(1s, 10% of duration)`, retried at 0 s if that seek finds nothing. Only when the probe found a real video stream — audio never gets a frame.
3. Otherwise `None`. Captions-only runs have no media, so step 2 does not apply.

**Encoding** (`encode_thumbnail`): stdin→stdout pipes, no temp files. `scale='min(320,iw)':'min(320,ih)':force_original_aspect_ratio=decrease` (shrinks, never enlarges, keeps aspect), mjpeg at `-q:v` 4 → 7 → 11 → 16 → 23 → 31 until ≤ **20 KB** (hard ceiling); if even q31 is over, the side steps down 320 → 240 → 180 → 120 → 80. Undecodable input stops after one attempt. Every ffmpeg/ffprobe call has a 15 s deadline and is killed on timeout or cancellation. Measured on the real binaries in the tests: a 1280×720 test pattern poster → 10.2 KB at 320×180; a 1920×1080 pure-noise image (near JPEG worst case) → 13.9 KB; a rotated 1280×720 phone clip's frame → 10.3 KB at 180×320.

## `TEMP_DIR` is validated at startup, and why it has to be

`validate_temp_dir` runs from **both** entry points — `api/app.py`'s
`lifespan` and `worker/settings.py`'s `startup` — and refuses to boot on a
`TEMP_DIR` that is not an absolute path for the host OS, cannot be created, or
is not writable. It creates the directory as part of that check.

"Absolute" is judged by the OS the process runs on, with that OS's path module
(`_require_absolute_for_host`, `_host_is_windows`): on Linux (the container)
`posixpath.isabs`, so `C:/...` is refused, which is the case below; on native
Windows `ntpath.isabs`, so a drive or UNC path passes and `/tmp/videolens`
(the `.env.example` default) is refused, because it has no drive. Each message
names its own OS: a local native-Windows run (no Docker) needs `TEMP_DIR` set
to something like `C:/Users/<you>/AppData/Local/Temp/videolens` in
`backend/.env`. Before 2026-11-26 the check used `os.path.isabs` with a
message about POSIX paths, which was wrong on Windows. Tests in
`tests/infrastructure/media/test_uploads.py` patch `_host_is_windows` and
`os.makedirs`, so both branches run on any host.

This exists because of a real production failure. The dev deployment had a
Railway service variable `TEMP_DIR` set to
`C:/Users/.../AppData/Local/Temp/videolens` — a Windows path carried into a
Linux container, almost certainly copied from a local `.env`. Nothing in the
repo said this: `config.py`, `backend/Dockerfile`, `backend/.env.example` and
`docker-compose.yml` all say `/tmp/videolens`, and an environment variable
overrides the Dockerfile's `ENV`, so it was invisible to code review, CI and
tests alike.

What made it genuinely hard to catch is that **it did not fail where it was
wrong**:

- `C:` is a legal directory name on Linux, so the old bare
  `os.makedirs(temp_dir)` at import time *succeeded*, quietly creating a
  relative `./C:/Users/...` tree next to the process. Startup reported
  healthy.
- yt-dlp then downloaded into that junk directory without complaint, so the
  `downloading` stage went green.
- FFmpeg was the first component strict enough to object, because it reads
  everything before the first colon of an output filename as a protocol
  scheme. It saw `C`, found no such protocol, and failed the run with
  `Protocol not found` at the `normalizing` stage — a media-looking error,
  several steps removed from the actual cause, and only on runs that got
  that far.

The old import-time `os.makedirs` was removed with this change; it was the
thing hiding the misconfiguration, not a safety net. `create_run_dir` still
creates per-run subdirectories as before.

**Download deadline and pool** (since 2026-11-20, `DOWNLOAD_DEADLINE_SECONDS`, default 300). Each socket read had a timeout (30 s direct HTTP, yt-dlp's `socket_timeout`), but nothing bounded the whole: a server sending a byte every 25 s held a worker slot until the arq job timeout, and info extraction could do the same across many requests. Every link fetch (`DirectHttpResolver`, `ytdlp_downloader.download_url`, `captions.fetch_captions`) now runs through `run_download(seconds, fn)`, which runs `fn(deadline)` on `DOWNLOAD_EXECUTOR` (8 threads named `videolens-download`, so downloads no longer share the default executor with everything else) inside a `DownloadDeadline`. The deadline is checked in the direct HTTP read loop (which reads with `read1`, so a trickle returns per chunk instead of waiting to fill 1 MB), in the yt-dlp progress hook (every chunk and fragment), in `GuardedYoutubeDL.urlopen` (every request yt-dlp makes, extraction included) and in the caption track read. A read already blocked is ended too: the pinned connections in `net.py` register their socket with the thread's deadline, and when it fires a timer shuts those sockets down (and closes them on Windows, where shutdown does not wake a blocked `recv`). A deadline that ends a download is a `MediaValidationError` ("This link took too long to download. Try again, or upload the file instead."), so the chain and caption fallback treat it like any other failed route; the caption path returns `None`.

**One budget per run (2026-11-20 re-review).** Each route used to get the full `DOWNLOAD_DEADLINE_SECONDS`, so yt-dlp, then direct HTTP, then the caption fallback could take three times it. `MediaService.download_url` now calls `deadline.start_run_budget(seconds)`, a `ContextVar` holding when the run's budget ends; each `run_download(..., run_budget=True)` (yt-dlp, direct HTTP, captions) reads what is left before it dispatches to the pool (the executor does not copy the context) and gets `min(seconds, left)`; with nothing left it raises `DownloadDeadlineExceeded` without calling the fetch. The default 300 s is the whole link download, under the 600 s job timeout. **TLS reads are ended too**: `PinnedHTTPSConnection.connect` used to track the raw socket, which `wrap_socket` detaches, so a deadline could not end a blocked TLS read; it now wraps with `do_handshake_on_connect=False`, tracks the `SSLSocket`, then handshakes (so a stalled handshake is covered as well). Verified on Windows, where the deadline also closes the socket; the Linux shutdown-only path is the same code but was not run here. **A deadline that had already fired** (2026-11-21 second re-review) shut the socket the moment it was tracked; on Linux the handshake then raised `AttributeError` (shutdown clears the SSL object) and on Windows `wrap_socket` an `OSError`, both reported as "This link couldn't be downloaded." `net._check_deadline` now runs after each socket is tracked (raw and TLS) and after a failed handshake, raising `DownloadDeadlineExceeded`, which urllib passes through unwrapped, so the user sees "took too long". Tested with the Linux path simulated (the deadline module's `os.name` swapped) and natively on Windows.

**yt-dlp read ceiling (2026-11-20 re-review).** yt-dlp reads some responses whole (`response.read()` with no size: webpages, manifests, API JSON), and its `HTTPHandler.http_response` inflates a gzip/deflate body whole inside `urlopen`, so a hostile server could make it hold an arbitrary body in memory. `ytdlp_net.MAX_UNSIZED_READ_BYTES` (20 MB) bounds both: `GuardedYoutubeDL.urlopen` wraps the response so an unsized `read()` takes at most that and fails with a `TransportError` past it (sized reads, which `HttpFD` uses for media in chunks, pass through), and `_PublicHTTPHandler` caps the encoded read and inflates with a bounded `decompressobj`. `br` is not installed, so never inflated.

**FFmpeg timeouts** (since 2026-11-20). `probe_duration_seconds` (run by the API on every upload), `_has_video_stream` and `normalize_media` awaited `communicate()` with no limit, and a cancelled job left the child running. All three, and the thumbnail calls (`thumbnails._run`), go through `process.run_process`, which kills and reaps the process on timeout and on any cancellation. ffprobe: `FFPROBE_TIMEOUT_SECONDS` = 30; the re-encode: `NORMALIZE_TIMEOUT_SECONDS` = 1200 (under the long-job timeout; a standard job is cancelled at its own 600 s first, which now kills ffmpeg too); thumbnails keep 15 s. A timeout is the same `MediaValidationError` as an unreadable file, with the timeout in `log_detail`.

**Known limits**: through an operator-configured proxy, connections are checked by URL but not pinned (the proxy resolves), for yt-dlp and urllib alike. The yt-dlp guard depends on yt-dlp internals (`UrllibRH`, its `HTTPHandler`/`RedirectHandler`, `YoutubeDL.build_request_director`/`dl`, `downloader.hls.FFmpegFD`); `test_ytdlp_net.py` exercises each, so a yt-dlp bump that changes them fails CI rather than quietly opening a path. Checked against yt-dlp 2026.10.26.

**Input protocols and playlists (fixed 2026-11-20 re-review)**: ffmpeg picks the demuxer from the content, so a playlist named `.mp4` could in principle make ffprobe (API, intake) or ffmpeg (worker) open the URLs it lists. Two layers now: `ffmpeg.INPUT_PROTOCOLS` (`-protocol_whitelist file`, inherited by nested opens) is on both ffprobe calls, both normalize commands and the thumbnail probe and frame extract (the stdin encode gets `pipe`); and `_refuse_playlist` reads the first 64 bytes before ffprobe and refuses text that opens like HLS, ffconcat, DASH/XML or SMIL (after a UTF-8 BOM and whitespace) with the unreadable-file message and `log_detail` "refused before ffprobe: the content is a playlist or manifest". **Since 2026-11-21** (second re-review: a DASH manifest opening with an XML comment, or with a lowercase `<mpd`, passed the first signature list, and ffprobe, which sniffs `<mpd` in any case anywhere in its probe buffer, opened it as DASH and read local segments) the sniff refuses any file whose first non-blank byte is `<` or `#` (or that starts `ffconcat`): no accepted container starts with either (`.mp3` opens with `ID3` or an 0xFF frame sync, `.mp4`/`.mov` with a box size and type). The one binary case that can look like it, an MP4/MOV whose first box is so large (over ~150 MB) that its size's first byte is a whitespace byte, is let through when bytes 4-8 are a top-level box type (`ftyp`, `mdat`, `moov`, `free`, `skip`, `wide`, `pnot`, `uuid`, `styp`). Second line of defence: the intake probe now asks for `format=format_name,duration` (keyed output) and refuses a file ffprobe opened with a demuxer that reads other inputs (`hls`, `dash` or any name containing `dash`, `concat`, `imf`, `smil`, `sdp`, `rtp`, `rtsp`; `log_detail` "refused after ffprobe"), even when it has no duration. ffprobe has already opened such a file by then, so this stops the worker from ever processing it; the whitelist still limits what it could open to local files. Locally (ffmpeg 8.1.1) the playlists made no request even without the whitelist; the container's ffmpeg was not checked, which is why the whitelist matters.
