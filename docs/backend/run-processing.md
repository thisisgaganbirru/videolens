# Run processing pipeline

Does the actual work for one run: get the source media onto disk, validate/normalize it, analyze it with Gemini, persist the result. Runs identically whether invoked by the local in-process runner or the arq worker — it has no idea which.

**Files**
- `backend/app/application/process_run.py` — `ProcessRunUseCase.execute()`, the whole pipeline.
- `backend/app/interface/worker/settings.py` — arq's `process_run` job function, which is a thin wrapper calling this use case.
- `backend/app/infrastructure/queue/job_queue.py` — the local (non-distributed) path calls this use case's `execute` directly as a bound callable (`local_runner`).

**Flow**
1. Status → `PROCESSING`.
2. Get the source onto disk, one of three ways: (a) `source_key` set → download from S3 via `ObjectStore.download_source`, then re-run the duration cap (the file wasn't validated in this process before); (b) `source_url` set → stage `"downloading"`, then `MediaProcessor.download_url`, then duration cap; (c) neither set → `saved_path`/`run_dir` were passed in directly (local-mode upload, already duration-capped by `CreateRunUseCase` before enqueueing — **not** re-validated here).
   - For path (b), if the download returned a `SourceMetadata` (yt-dlp's own post metadata — title, uploader, caption, upload date, like/view/comment counts; see `docs/backend/media-validation.md`), it's persisted immediately via `RunRepository.set_source_metadata` — before normalize/analyze — so it's visible on `GET /api/runs/{id}` even if a later stage fails. File-upload runs never have this (`SavedUpload.metadata` is `None` for uploads).
   - Paths (a) and (b) record the length `enforce_duration_cap` returns via `RunRepository.set_duration` (`_record_duration`, which logs and swallows a write failure — the duration is cosmetic and must never fail a healthy run). The caption fallback records `CaptionTrack.duration_seconds` (yt-dlp's reported length) the same way.
3. If no usable path/dir resulted, raise `MediaValidationError("No media source was provided.")`.
4. Stage → `"normalizing"`, then `MediaProcessor.normalize_media`.
5. `AnalysisEngine.analyze_with_retry`, with an `on_stage` callback that relays Gemini's own stages (`"uploading_to_gemini"`, `"analyzing"`) into `RunRepository.set_stage`, and the `SourceMetadata` from step 2 when there was one. The metadata is both persisted onto the run *and* passed to the engine — persisting it makes it visible in the UI, passing it makes the analysis better (see `docs/backend/gemini-analysis.md`). Upload and S3 paths pass `None`.
6. `RunRepository.set_result` on success, with `AnalysisCompleteness.FULL`.

**History poster (Phase 5a)**: as soon as the source is on disk (after the duration cap on paths (a)/(b); right after step 3 on path (c)), `_start_visuals` launches `MediaProcessor.describe_visuals` as an `asyncio` task that runs **alongside** normalize/analyze, so it adds no latency. Inputs: the local file plus, for URL runs, yt-dlp's `thumbnail_urls`/`width`/`height` hints from `SavedUpload`. `_record_visuals` awaits it and writes `RunRepository.set_visuals` **immediately before** `set_result`, so the first poll that sees `complete` already carries `thumbnail`/`width`/`height`. The caption fallback does the same with `CaptionTrack`'s hints and no file. Every failure (the capture raising, the write raising) is logged and swallowed — a missing poster never fails a run. On any failure/cancellation path `finally` cancels an unfinished capture (`_discard_visuals`) **before** `cleanup_run_dir` deletes the file it may be reading. Failed runs get no visuals.

**Caption fallback (URL runs only)**: if step 2(b) raises `MediaValidationError` — every resolver in the chain failed — the pipeline tries `MediaProcessor.fetch_captions` before giving up. Platforms serve subtitles from a different pipeline than media bytes, so a 403 on the video very often coexists with a perfectly available caption track. On success the run completes with stage `analyzing_captions`, `AnalysisCompleteness.CAPTIONS_ONLY`, and a text-only analysis (`AnalysisEngine.analyze_captions`, see `docs/backend/gemini-analysis.md`); `SourceMetadata` recovered alongside the captions is persisted too. Verified end-to-end against a YouTube URL that returns `HTTP 403` on download.

Any failure inside the fallback returns False and the **original download error** is re-raised — the caption attempt is a bonus and its own problems must never replace the diagnosis of why the download failed. Upload and S3 runs never enter this path (there is no URL to fetch captions from).

**Error handling — three distinct paths**, all terminal (none re-raise out of `execute`):
- `MediaValidationError` / `GeminiConfigurationError` → stored verbatim as `run.error` (these already carry a caller-safe message).
- `asyncio.CancelledError` → **re-raises** after one of two writes. This branch exists because `CancelledError` is a `BaseException`, so the catch-all below never sees it. Two causes look identical from inside the job: arq's `job_timeout` (arq raises `TimeoutError` outside the coroutine and never retries it; arq 0.28 `worker.py`, `asyncio.wait_for` around the job task) and a worker shutdown (SIGTERM on deploy: arq cancels the task, logs "cancelled, will be run again" and re-queues it). The worker passes `deadline` (event-loop time at which the job's timeout fires, taken before the vault read); a cancellation more than 1 s before it is a shutdown. Since 2026-11-20:
  - **Timeout, no deadline (the in-process runner), or an own-key run**: marks the run failed with `RUN_INTERRUPTED_MESSAGE`; `finally` settles everything as for any failure. An own-key run cannot be retried: its key was single-use and is gone, and it must never fall back to the shared key.
  - **Shutdown (`resumable`)**: sets the run back to `queued` (which also re-arms the stale-run clock) and leaves it for arq's retry. `finally` then releases nothing: the free-run hold, the extra-run ledger row and the long-run slot stay held and the S3 source stays, so the retry settles each exactly once as any run does. Only a daily cap unit this attempt already spent on Gemini is settled now, without refund, so the retry finds no hold and cannot refund it. The run directory is removed either way (the retry fetches the source again). `max_tries = 2`, so one shutdown retry; a second one exceeds it, arq gives up without calling the job, and the read-time stale check fails the run and refunds its free run.
  Both writes are best-effort (the loop may already be tearing down), which is what the read-time staleness check backstops.
- Anything else → logged with `logger.exception`, but the *stored* `run.error` is always the fixed string `"Media analysis failed. Please try again."` — deliberately masks internals (stack traces, credentials, third-party error text) from ever reaching the client via run status. Trade-off: debugging a failed run from its stored error alone tells you almost nothing; you need the server logs for the real cause.

**Free-run refund (`finally`, always runs)**: `_settle_free_run` calls `FreeRunAllowance.release(run_id, refund=rejected_before_analysis)`. `rejected_before_analysis` is set only on the link path (b), before any Gemini call: when `download_url` raised and the caption fallback did not complete the run, or when `enforce_duration_cap` raised on the downloaded file. It stays false for a caption path that failed at Gemini (the cap is never checked there), normalize, analyze, cancellation and uploads (including path (a)'s duration re-check; intake refunds over-long uploads). Release is a no-op for runs that held no free run (BYOK, allowance off) and refunds at most once. A failing release is logged and swallowed. See `free-runs.md`.

**Cleanup (`finally`, always runs)**: if `source_key` was set, deletes the S3 object — failure to delete is logged and swallowed, doesn't affect run status. Then always calls `MediaProcessor.cleanup_run_dir`.

**Abandoned runs** (the previously-documented "known issue", corrected 2026-08-29): the old note claimed a local-mode restart left a run `PROCESSING` forever. That is not what happens — in local mode `RunStore` is an in-process dict too, so a restart discards the run entirely and it returns 404. The real stranding cases were different, and both are now handled:

1. **A garbage-collected local task.** `RunQueue` dispatched local runs with a bare `asyncio.create_task(...)` and kept no reference. The event loop holds only a *weak* reference, so the task could be collected mid-run: the coroutine stops, the process lives on, and the run is stranded in `PROCESSING` in a store that is still very much alive. Fixed by holding the task in `RunQueue._local_tasks` until its done-callback discards it.
2. **A cancelled distributed job.** arq's `job_timeout` cancellation was never caught (see the error-handling list above). Since 2026-11-20 a shutdown cancellation is left for the retry instead of failed.
3. **Backstop for everything else** — OOM kill, container replacement, any death that gives the process no chance to write. `GetRunUseCase` treats a `queued`/`processing` run whose `updated_at` is older than `worker_job_timeout_seconds + 120` as abandoned (`domain/policies.py:is_run_stale`), reports it as failed, and persists that so history agrees. This is the only mechanism that does not depend on the dying process cooperating. It hands back the free run, voids the extra-run row and, when the run's stage shows it never reached Gemini, refunds the daily cap unit (2026-11-20; `cost-abuse-protection.md`).

`ListRunsUseCase` deliberately does **not** apply the staleness check — it would turn a history listing into a write path.

**Tests**: `backend/tests/application/test_process_run.py` — covers all three source-acquisition paths, all three error paths (including that the masked-message path really doesn't leak the original exception text), that cleanup still runs even if `delete_source` itself throws, that `SourceMetadata` reaches the analysis engine on URL runs while uploads analyze with `None`, the full caption-fallback matrix (recovery, no captions, broken fetch, failing caption analysis, uploads never trying it), and that a cancelled job is marked failed and still propagates the cancellation. Phase 5a adds: visuals written while still `PROCESSING` (before complete) on link/S3/local-upload/caption paths, the exact hints passed per path, audio writes nothing, a raising capture or write never fails the run, and a failed analysis cancels an unfinished capture before cleanup. `FreeRunDownloadRefundTests` covers the free-run refund matrix. `backend/tests/application/test_get_run.py` covers staleness; `backend/tests/infrastructure/queue/test_job_queue.py` covers the local task reference.

## Multi-slide posts (2026-11-26)

When `download_url` returns `SavedUpload.slides` (an Instagram carousel or single-photo post, `media-validation.md`), `execute` takes the slide branch at three points and nothing else changes: `enforce_slides_cap` instead of `enforce_duration_cap` (the returned total feeds the long-run claim as before), `normalize_slides` instead of `normalize_media`, and `analyze_slides_with_retry` instead of `analyze_with_retry`. It records `Run.slide_count` (`set_slide_count`, a media fact: a failed write is logged and swallowed like the duration) and the video slides' total as `duration_seconds`, which is left unset when every slide is an image. The poster is captured from the first slide with yt-dlp's hints for it, without a duration (the total says nothing about the first slide). `slide_count` is returned by `GET /api/runs/{id}` and `GET /api/runs`, and saved in a paid account's saved source. Tests: `tests/application/test_process_run_slides.py`.

**Slide pictures (2026-11-27, owner decision).** The same `_start_visuals` call is given `slides=downloaded.slides` (the downloaded files, already probed by `enforce_slides_cap`), so the slide pictures are made in the existing visuals task: concurrently with `normalize_slides` and Gemini, never sent to Gemini, and cancelled by `_discard_visuals` before the run directory is removed on a failure. `MediaService.describe_visuals` makes the poster first, then `thumbnails.build_slide_thumbnails`: one `SlideVisual(slide, kind, thumbnail)` per slide, numbered from 1 in the post's order (the tuple the analysis numbers `screen_text_segments[].slide` by), one slide at a time. Each is a JPEG data URL, longest side at most 480 px (never enlarged), q:v 5 then stepped down to a hard 80 KB per slide; a video slide is a frame taken as the poster's is (~1 s in, 0 s if that finds nothing). A slide that fails is `thumbnail: null` and the run is unaffected. The set is capped at 1.2 MB of data URLs (`SLIDE_THUMBNAILS_BUDGET_BYTES`; the slide that would pass it and all later ones are null) and 25 s (`SLIDE_THUMBNAILS_DEADLINE_SECONDS`, with a 30 s backstop `SLIDES_TIMEOUT_SECONDS` in `service.py`). The poster keeps its own 45 s timeout and the slides run after it under theirs, so a slow or failed slide set only ever costs the slides and a poster timeout still leaves them. Worst case the visuals task can take ~75 s, and `_record_visuals` waits for it before `complete`; in practice it is done long before Gemini answers. Time taken and counts are logged at debug. `_record_visuals` writes them with the poster through `set_visuals`, just before `set_result`, so `Run.slides` appears with `complete` (earlier would make every poll carry them) and is also written when the poster came back empty. Returned as `slides` on `GET /api/runs/{id}` only (not the list), null for one media file. A single-photo post has `slide_count` 1 and one item. Not saved in a paid account's saved history (`saved-history.md`) and not part of a share. Tests: `tests/application/test_process_run_slides.py`, `tests/infrastructure/media/test_slide_thumbnails.py`.

## Limits and the long-run slot (2026-11-13)

`execute(..., limits=)` receives the `MediaLimits` the API admitted (rebuilt from the `limits` job kwarg in the worker). They go to `download_url`, both `enforce_duration_cap` calls and `fetch_captions`, so the worker enforces the run's own numbers.

**Own-key runs without a key (every BYOK run, 2026-11-13)**: before anything else, a run that reached `execute` with no key is checked by `_refuse_without_own_key`. If its record says `admitted_byok` (or its limits are the signed-in BYOK tier), it fails with `OwnKeyUnavailableError`: "This run waited too long to start. Please try again." while still `queued`, "Analysis was interrupted before it finished. Please try again." when an earlier arq attempt had set it `processing`; a `complete`/`failed` run is left alone. A run with no record left is not started. The refusal releases the slot and deletes the files, then returns before the `try`, so the `finally` never runs for it. Never the shared key (`byok.md`).

One extra step for runs admitted under the signed-in BYOK limits:
- After a link's download and duration probe, a run above the standard limits claims the account's long-run slot (`LongRunGuard.try_acquire`); if another run holds it, this run fails with "You already have a long video processing. Wait for it to finish." (a polled `error`, since the 429 at intake only applies to uploads). An S3-sourced upload re-claims the slot its intake took (idempotent per `run_id`). The `finally` block releases the slot. The caption fallback does not claim it.

## Runs that ended elsewhere (stale-run skip, 2026-11-13)

The read-time staleness check (`GetRunUseCase`, abandoned-run backstop 3 above) can fail a run whose arq job is still waiting in the queue or still running. The worker no longer spends download, FFmpeg or Gemini on such a run:

- **At the start** (`_drop_before_start`, one `runs.get`, merged with the own-key refusal): a run whose record is gone, or that is already `complete`/`failed`, does no work. It deletes the S3 source and the run directory, releases a long-run slot it holds, settles its free run, and returns before the `try` (so the `finally` never repeats any of that). A `failed` run's held free run is refunded (the person got nothing); a `complete` run (a retry of a finished job) and a recordless one are released without refund. The own-key refusal (`OwnKeyUnavailableError`) is the third branch of the same check and is unchanged for a live run; a run that is already `failed` keeps the sweep's message.
- **Checkpoints** (`_ensure_not_ended`, one `runs.get` each): before normalize, before the Gemini analysis, and before the caption fallback's Gemini call. A run that ended raises the module-private `_RunEndedElsewhere`; `execute` logs a warning, writes nothing, and its `finally` cleans up as usual, refunding the free run when the run is `failed`. The caption path re-raises it rather than reporting the original download error.
- **The final write cannot resurrect a failed run.** `RunStore` never writes to a `complete`/`failed` run again (see `run-storage.md`): `set_result` returns False, the pipeline drops the result (Gemini was already spent) and the run stays failed. Decision: the failure stands rather than completing. The client already saw `failed` from the poll that swept it, stopped polling and filed the run as failed in History; completing it afterwards would show a different outcome only to a client that happens to read again.
- **The reverse race**: the sweep read the run as stale, then the worker completed it before the sweep's write. The store refuses the sweep's `set_error`; `GetRunUseCase` re-reads and returns the completed run, and refunds nothing.

`RunStore` makes the check and the write one step (a Lua script in Redis, the lock in memory), so of the worker's result and the sweep's failure exactly one lands.

**Tests**: `backend/tests/application/test_stale_run_skip.py` (link and S3 jobs for a swept run do no work and clean up; slot released; refund once across sweep, worker and arq retry, device and account; recordless and completed runs not refunded; swept during download, normalize, Gemini and caption fetch; the sweep losing the race; normal runs and the own-key refusal unchanged) and `EndedRunsAreFinalTests` in `tests/infrastructure/persistence/test_run_repository.py`.
