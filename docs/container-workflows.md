# Container and environment workflows

VideoLens has three deliberately separate execution paths. Local development
uses Docker Compose; the `dev` branch validates and publishes dev artifacts;
the `main` branch validates and publishes production artifacts. A Compose file
is never reused as a hosted deployment manifest.

## Environment boundaries

| Scope | Entry point | Runs | Publishes or deploys |
| --- | --- | --- | --- |
| Local workspace | `scripts/workspace.ps1` and `docker-compose.yml` | Hardened frontend, API, worker, Redis, and MinIO on loopback/private networks | Nothing external |
| Pull request | `.github/workflows/pull-request-checks.yml` | Application checks, native container builds/scans, and the Android build/unit tests for PRs targeting `dev` or `main` | Nothing |
| Dev | `.github/workflows/development-environment.yml` on `dev` | Application checks and container checks | Signed amd64/arm64 images tagged `dev` and `sha-<commit>` in GHCR |
| Android dev | `.github/workflows/android-development-build.yml` on `dev` | Android API 36 build and unit tests | Debug artifact and dev prerelease |
| Production | `.github/workflows/production-environment.yml` on `main` | Application checks, container checks, and the Android build/unit tests | Signed amd64/arm64 images tagged `latest` and `sha-<commit>` in GHCR |

Workflow filenames use lowercase kebab-case. Call-only building blocks follow
`reusable-<responsibility>.yml`; event-driven entry points follow
`<scope>-<purpose>.yml`. The environment workflows orchestrate reusable
application, container, and publication logic without duplication.

### Android gating

The Android build exists in exactly one place,
`.github/workflows/reusable-android-checks.yml` (Capacitor sync, `gradlew
assembleDebug testDebugUnitTest`). It is capped at `contents: read` and never
creates a tag or a release. Three callers:

- `pull-request-checks.yml` — pre-merge gate. Nobody builds Android locally, so
  this is the only thing that catches a broken Capacitor sync or Gradle build
  before it lands. It costs roughly 6-10 minutes of extra PR CI wall-clock, in
  parallel with the application and container jobs.
- `production-environment.yml` — same gate on `main`. It does not block the
  container publication job, which has no Android dependency; an Android failure
  still fails the workflow run.
- `android-development-build.yml` — passes `upload_apk: true`, so the reusable
  also writes `version.json` and uploads the APK as a workflow artifact. A
  separate `release` job in that workflow (the only job holding
  `contents: write`) downloads the artifact and publishes the dev prerelease.

The release step passes `target_commitish: ${{ github.sha }}`. Without it GitHub
creates the tag at the repository default branch (`main`) while the APK is built
from the pushed `dev` commit, so the tag does not describe the artifact —
observed on `dev-v1.1.0-build28`. `workflow_dispatch` runs build and test only;
the release job is gated on `github.event_name == 'push'`.

### Release notes

The release body comes from `generate_release_notes: true` — GitHub composes it
from the pull requests merged since the previous tag. This depends on
`target_commitish` being correct: the notes are generated by diffing against the
previous tag's history, so a tag created on the wrong branch would have produced
notes describing the wrong range. The two settings are coupled; do not remove one
without reconsidering the other.

`frontend/public/releases.json` remains a release *index* — name, tag, date, and
URL per entry, capped at 20 — not a changelog. It carries no `body` field, so the
in-app Releases panel links out to the GitHub release for the description rather
than rendering it inline. `softprops/action-gh-release` exposes only `url`, `id`,
`upload_url`, and `assets` as step outputs; the generated body is not among them,
and retrieving it would require a second authenticated API call against the
release `id`. That was judged not worth the coupling — a body field that is
sometimes empty would render blank sections in the panel.

## Local workspace

Create `backend/.env` from `backend/.env.example`, then use:

```powershell
.\scripts\workspace.ps1 check
.\scripts\workspace.ps1 up
.\scripts\workspace.ps1 verify
.\scripts\workspace.ps1 test
.\scripts\workspace.ps1 scan
.\scripts\workspace.ps1 down
```

`down` preserves named Redis and MinIO volumes. Compose credentials have
development-only defaults and all published ports bind to `127.0.0.1`.

`test` bind-mounts `backend/tests` into the running container read-only. That is
not a convenience — `backend/.dockerignore` excludes `tests/`, so the suite is
not in the image and `python -m unittest discover -s tests` would find nothing
without the mount. If that exclusion is ever removed, drop the mount too.

The application images run as fixed non-root users with all Linux capabilities
dropped, a read-only root filesystem, `no-new-privileges`, PID/resource limits,
health checks, and writable `tmpfs` only where required. Redis and MinIO use
pinned image digests and live only on the internal data network; only the MinIO
console has a loopback host port.

## Build and supply-chain controls

- Backend dependencies are compiled from `backend/requirements.in` into the
  hashed universal lock at `backend/requirements.txt`. Regenerate it with
  `uv pip compile backend/requirements.in --generate-hashes --python-version 3.11 --universal -o backend/requirements.txt`.
- Dockerfiles use pinned base-image digests and multi-stage/cache-mounted
  builds. Runtime images exclude package managers and build tooling where
  possible.
- Container checks run Dockerfile validation, cached native builds, and fail on
  fixable high or critical vulnerabilities.
- Publications build `linux/amd64` and `linux/arm64`, attach maximum provenance
  and an SBOM, and publish a commit-addressable tag.
- **Images are deliberately not signed.** Keyless Cosign signing was removed: it
  writes a permanent, undeletable entry to Rekor, the public Sigstore
  transparency log, recording the repository identity, workflow ref, and image
  digest. An irreversible public emission does not fit this project's posture
  while it is still private. Keyless signing cannot be kept without that log —
  the short-lived Fulcio certificate is only verifiable through Rekor, so
  `--tlog-upload=false` would produce a signature nobody can verify. If signing
  is wanted later, it needs a self-managed key pair, not the keyless flow.
  Removing it also let `id-token: write` drop from all three publication-path
  workflows; Cosign was the only OIDC consumer (GHCR login uses
  `secrets.GITHUB_TOKEN`).
- `provenance: mode=max` and `sbom: true` are kept. They are BuildKit
  `--attest` shorthands: the resulting in-toto attestation manifests are pushed
  into the image index in GHCR alongside the image, and are not Sigstore-signed
  and not logged anywhere public. One caveat that follows from `mode=max`: it
  records build arguments and full build-step metadata into that attestation, so
  never pass a secret via `build-args` — use the `secrets` input instead. Today
  the only build arg is `NEXT_PUBLIC_API_BASE_URL`, which is compiled into
  client-side JS and therefore public by construction.
- Third-party GitHub Actions are pinned to commit SHAs. Dependabot monitors
  Docker, Actions, npm, and Python dependency sources.
- Dependabot's Docker ecosystem bumps base-image digests only; it never looks
  inside a `RUN` layer. Package constraints written there (`apk add`, `pip
  install`) must therefore be `>=` security floors, not exact pins — an exact
  pin breaks the build the moment the distro repository advances past it, and
  nothing will ever open a PR to fix it. Quote the constraint
  (`'openssl>=3.5.7-r0'`), or the shell reads `>` as redirection and drops it
  silently.

## Dev and production hosting

Railway project `videolens` already has a populated `dev` environment. Its API,
worker, frontend, Redis, and object storage remain source-wired to the `dev`
branch; Railway performs the actual dev deployment. The GitHub dev workflow is
the independent validation and artifact-publication lane and compiles the
frontend against `https://videolens-backend-dev.up.railway.app`.

Railway `production` currently has no service instances. The production GitHub
workflow therefore publishes release-ready images but does **not** pretend to
deploy them. Provision and configure production API, worker, frontend, Redis,
and object storage first; then add an explicit deployment job as separate work.

`PRODUCTION_API_BASE_URL` is required by the **frontend** publication leg only,
because only the frontend image compiles a backend URL in. If the GitHub
`production` environment does not define it, the frontend leg fails loudly at
its validation step while the backend leg still publishes — the matrix sets
`fail-fast: false`, and the requirement is scoped by `matrix.service`. A missing
production API base URL cannot block an image that has no use for it.

Configure GitHub environments named `dev` and `production`. Production should
require reviewer approval and restrict deployment branches to `main`. Branch
protection should require the pull-request application, container, and Android
jobs.

## Known issues

- Both architectures are configured in the publication workflow. Native amd64
  builds are verified locally; the optional local emulated arm64 verification
  was interrupted, so the first successful publication workflow remains the
  arm64 proof.
- GitHub environment protection and branch protection are repository settings,
  not files, and must be configured by a repository administrator.
- Railway's source integration can begin a dev deploy independently of the
  GitHub validation lane. If strict pre-deploy gating is required, configure
  Railway check-suite waiting after these workflow names exist on the remote.
